# 01 · 架构总览

> 目标读者：第一次接触本仓库、准备改代码的人。
> 读完应能回答：数据从键盘到声卡/文件是怎么走的、每层负责什么、哪些东西**故意**没有做。

---

## 1. 一句话架构

**纯函数内核（`Core`）+ 自绘 UI（`Editing`）+ 一个编排窗口（`MainWindow`）。**

```text
       键盘 / 鼠标 / 输入法
              │
              ▼
   ┌───────────────────────┐
   │  Editing              │   自绘编辑器（WPF FrameworkElement）
   │  EditorTextView       │   · 文本缓冲 / 选区 / 撤销 / IME
   │  TextBuffer           │   · 可见行虚拟化渲染
   └──────────┬────────────┘
              │ string（全文）
              ▼
   ┌───────────────────────┐
   │  Core.Syntax          │   AttmParser.Parse(text) → ParseResult
   │  Lexer → Parser       │   { Score?, Diagnostics[], Tokens[], LineStarts[] }
   └──────────┬────────────┘
              │ Score（绝对 tick）
      ┌───────┴────────┐
      ▼                ▼
┌──────────────┐  ┌──────────────┐
│ Core.Midi    │  │ Core.Playback│
│ SMF 写入器    │  │ ScorePlayer  │──► IMidiOutput ──► winmm ──► 系统 MIDI 端口
└──────┬───────┘  └──────────────┘
       │
       ▼
   *.mid 文件（保存时与 .attm 同名产出）
```

## 2. 分层与依赖规则

| 层 | 命名空间 | 依赖 | 能否引用 WPF |
| --- | --- | --- | --- |
| 语法内核 | `ATTM.Core.Syntax` | 无（仅 BCL） | **否** |
| MIDI 内核 | `ATTM.Core.Midi` | `Core.Syntax` | **否** |
| 播放内核 | `ATTM.Core.Playback` | `Core.Syntax`、`Core.Midi`、`System.Runtime.InteropServices`（winmm） | **否**（只有 P/Invoke） |
| 编辑器 | `ATTM.Editing` | `Core.Syntax` + WPF | 是 |
| 服务 | `ATTM.Services` | BCL + WPF（主题） | 是 |
| 视图 | `ATTM.Views` | `Services`、`Core.Playback` | 是 |
| 编排 | `ATTM`（MainWindow / App） | 以上全部 | 是 |

**硬规则**：`Core/*` 里出现 `using System.Windows*` 视为错误。这条规则让语法与 MIDI 逻辑可以在控制台测试工程里**直接跑**，不需要 UI 线程（`tests/ATTM.Tests` 正是这样做的）。

## 3. 一次编辑的完整数据流

以「用户在编辑器里打下一个 `1`」为例：

1. `EditorTextView.OnTextInput` 收到字符 → `InsertText("1")`
2. `ApplyEdit` 调 `TextBuffer.Replace`，重建行索引，`Version++`
3. 抛出 `BufferChanged` → `AttmEditor` 刷新行号槽/缩略图 → `MainWindow` 收到
4. `MainWindow.MarkDirty`（若有播放则先 `Stop`）→ `ScheduleParse` 启动 **180 ms 防抖**定时器
5. 定时器到点 → `Reparse()`：
   - `AttmParser.Parse(Editor.Text)` → `ParseResult`
   - `Editor.ApplyParse(result)`：高亮区间、诊断按行分组、行号槽错误行
   - `_player.SetScore(result.CanPlay ? result.Score : null)`
   - `UpdateStatus()` / `UpdateButtons()`
6. 播放时：`_playTimer`（10 ms，`DispatcherPriority.Render`）调 `ScorePlayer.Advance()`，把 12 ms 前瞻窗口内到期的 MIDI 短消息发出去；同时 `GetActiveSpans()` 回吐正在发声的源码区间给编辑器做高亮。

**关键点**：解析是**全量重解析**（不做增量）。语法文件只有几千行，实测 2000 行 < 1 秒（有专门的性能测试锁这条），全量最简单也最不容易错。

## 4. 核心数据模型

```text
Token(Kind, Text, Line, Column, Span)
   └─ 词法产物，同时被解析器和语法高亮复用

NoteEvent(Pitch, Velocity, StartTicks, DurationTicks, MeasureIndex, VoiceIndex, Span)
   └─ 绝对 tick 的音乐事件；Span 指回源码，用于播放高亮

Score { Bpm, KeyRoot, KeySharp, BeatsPerMeasure, BeatUnit,
        VelocityBase, VelocityJitter, TicksPerQuarter=480,
        MeasureCount, Notes[] }
   └─ 解析成功后的乐谱（可带错误，error 时 UI 禁止播放/保存）

ParseResult { Score?, Diagnostics[], Tokens[], LineStarts[], MeasureStartLines[] }
   └─ CanPlay = Score != null && !HasErrors
```

`MeasureStartLines` 是「从光标处播放」和「乐句预览」的定位基础：它记录**每个小节第一行的行号**，于是「光标在第 N 行 → 第几个小节」只是一次线性/二分比较。

---

## 5. 时间模型

- 所有时间是**绝对 tick**，从文件开头算。`TicksPerQuarter = 480`（PPQ 480，MIDI 通用值）。
- `MeasureTicks = 480 * 4 * BeatsPerMeasure / BeatUnit` → 4/4 为 **1920**，3/4 为 **1440**。
- 一秒对应多少 tick：`SecondsPerTick = 60 / (Bpm * 480)`。
- 最短音符：`MinUnitTicks = 480 / 32 = 15` tick（三十二分之一拍以下报 `E113`）。
- MIDI 与播放器**共用同一份时间轴**（`MidiSequence.BuildNoteMessages`），所以导出的 `.mid` 与听到的完全一致。

---

## 6. 线程模型

**单线程**：所有 UI 与播放调度都在 WPF 的 Dispatcher 线程上。

| 位置 | 机制 | 原因 |
| --- | --- | --- |
| 解析防抖 | `DispatcherTimer` 180 ms | 避免每个按键都全量解析 |
| 播放推进 | `DispatcherTimer` 10 ms @ `Render` 优先级 | 用定时器 + 12 ms 前瞻代替采样精确定时器，抖动可控且不阻塞 UI |
| `EnsurePhraseRoom` 宽度动画 | 自建 `DispatcherTimer` 16 ms | **不依赖 WPF 动画时钟**——离屏/虚拟显示环境里 `CompositionTarget.Rendering` 可能不推进，自驱动画才能在无头测试里跑完 |
| 系统主题变化 | `SystemEvents.UserPreferenceChanged` → `Dispatcher.BeginInvoke` | 该事件在系统线程触发，改资源字典必须回 UI 线程 |

没有后台线程、没有 `async`、没有并发集合。

## 7. 关键设计决策（含理由）

| 决策 | 理由 |
| --- | --- |
| **自绘编辑器**（`FrameworkElement` + `DrawingContext`）而不是 AvalonEdit / RichTextBox | 需要「可见行虚拟化 + 简谱语义高亮 + 源码区间高亮 + 精确字符宽度」四件事同时可控；RichTextBox 太慢且难拿到字符矩形，AvalonEdit 是一个 3 万行的依赖。自绘只有 1092 行。 |
| **零第三方 NuGet 依赖** | 体积（`ATTM.exe` 1.7 MB）+ 许可干净（只剩两个字体）+ 断网可构建。代价是 MIDI 写入器、拼音输入法对接、撤销栈全部手写。 |
| **空行分隔小节，连续行 = 并行声部** | 比「小节号/声部号」标注更贴近手写简谱的习惯，且让和弦与多声部共用一套排版规则。 |
| **休止符 `0` 截断前一个音** | 若 `0` 不占位，`1,0,0,0` 会被读成全音符，与直觉相反。让 `0` 占一个单元，时值规则就只剩一条：「一个音响到下一个单元开始」。 |
| **同音高重叠 → 后音截断前音**（`NoteMerger`） | 多声部写和弦时容易重复同一音高；截断比叠加两次触发更符合听感，也避免 MIDI 上出现悬空 NoteOn。 |
| **解析失败仍产出部分乐谱** | 用户改谱时状态栏还能显示 BPM/调式/音符数，错误只阻断播放与保存。 |
| **播放/暂停/停止不给快捷键** | 空格、`P`、`S` 在文本编辑器里都是输入键，抢走会破坏打字。只用工具栏。 |
| **保存强制双产物 `.attm` + `.mid`** | 谱面和音频永远同步，不出现「改了谱忘了导出」。 |
| **打开 = 打开谱库文件夹** | 自绘编辑器不做文件树，把「找文件」交给资源管理器最省事也最符合用户习惯。 |
| **配置损坏静默回退默认值** | 一个小工具因配置坏掉而打不开是最差的体验；所有 `AppConfig.Save/Load` 都吞异常。 |
| **文本统一 UTF-8 无 BOM + LF** | 跨平台（DAW、Git、编辑器）友好；读入时仍兼容 BOM / UTF-16 / GB18030 老文件。 |

## 8. 目录职责速查

| 路径 | 职责 | 不该放什么 |
| --- | --- | --- |
| `Core/Syntax` | 文本 → `Score` + 诊断 | UI 文案以外的任何界面逻辑 |
| `Core/Midi` | `Score` → `byte[]`（SMF） | 文件路径以外的 IO 策略 |
| `Core/Playback` | `Score` → 定时发送 MIDI | 窗口/控件引用 |
| `Editing` | 文本的显示与编辑 | 解析规则（只消费 `ParseResult`） |
| `Services` | 配置、主题、文件编码 | 业务规则 |
| `Views` | 模态对话框 | 主流程编排 |
| `MainWindow` | 把所有东西连起来 | 可复用的算法 |

## 10. 已知边界

- 单谱表、单轨、单通道（Channel 0，Program 0 大钢琴）。
- 拍号只支持 4/4 与 3/4（`E111`）。
- 调式根音只到「自然大调 + 可选升号」，没有小调、没有降号调号（降号用 `-1` 之类在音符层表达）。
- 播放不混音：一个进程只有一个 `IMidiOutput`，同一首不能分端口。
- 中文输入法候选框位置由系统决定，自绘控件只能保证**组合串在正确位置绘制**（见 `04-编辑器实现.md`）。
